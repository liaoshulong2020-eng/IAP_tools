# C/D 版本 IAP 工具共用性分析

本文用于说明 C 版本、D 版本、LLC、PFC 之间哪些工具可以共用，哪些只能条件共用，哪些必须分开维护。

## 总体结论

| 模块 | C/D 是否共用 | LLC/PFC 是否共用 | 结论 |
| --- | --- | --- | --- |
| `CAN_TOOLS_NET8.0` CAN 上位机 | 可以共用 | 可以共用 | 作为统一 CAN IAP 上位机维护，通过配置区分 C/D、LLC/PFC、固定 ID、节点 ID、波特率和包大小 |
| `11.iap_tools` 串口 IAP 上位机 | 可以共用 | 可以共用 | 协议层可以共用，当前主要用于对照旧串口升级流程和验证可靠性 |
| `IapFileCreator` 合并烧录工具 | 可以共用 | 可以共用 | 建议作为后续统一生成 JLink 合并烧录码和 IAP 包的标准工具 |
| `4.boot_config` | 可以改造成共用 | 可以改造成共用 | 当前路径和数据硬编码较多，建议后续改成配置表方式，不建议继续复制多份 |
| `4. 转发板源程序/5.CommKit-5800` 串口/CAN 转发板 | 条件共用 | 可以共用 | 如果转发板硬件和 MCU 不变，则可共用；如果转发板 MCU 也换 C/D 版本，则底层驱动需分版本 |
| `3. bootloader` | 不能直接共用 | 当前不直接共用 | C/D SDK、CAN/UART/Flash 底层不同，LLC/PFC 角色也不同，先分目录验证 |
| `5.原副边程序` APP 工程 | 不能直接共用 | 不能直接共用 | APP 与具体项目、芯片、功率板角色绑定，必须按版本维护 |
| `6.官方SDK` | 不能共用 | 可作为参考 | C 版本 SDK 和 D 版本 SDK 分开保存，只能按对应芯片引用 |

## 完全共用工具

### CAN 上位机 `CAN_TOOLS_NET8.0`

它运行在 PC 端，通过 ZLG CAN DLL 发包，不依赖 C/D 芯片 SDK。因此 C 版本和 D 版本可以共用同一个上位机。

需要靠配置区分的内容：

- 目标：LLC / PFC。
- CAN ID 模式：固定 ID `0xAA55` 或节点 ID `0xA0000~0xA0007`。
- CAN 通道和波特率，当前默认仍建议 `125kbps`。
- APP 起始地址 `0x08008000`。
- 参数区地址 `0x08007000`。
- 写包大小，当前可靠基线为 `128 bytes`。

后续建议：不要再复制多个 CAN 上位机工程，而是在同一个工具里增加“项目预设”，例如 `C-227B-T-LLC`、`D-259B-LLC`、`D-259B-PFC`。

### 串口 IAP 上位机 `11.iap_tools`

它是旧串口升级工具，核心依赖串口和 Modbus/IAP 协议，不依赖 C/D 芯片 SDK。只要 bootloader 协议和地址一致，它就可以同时用于 C/D 版本。

当前价值：

- 作为旧流程可靠性对照。
- 验证 APP 起始地址、参数区、CRC、包大小是否一致。
- 对比 CAN 直连升级和串口转发升级的时序差异。

后续建议：保留为通用串口 IAP 工具，增加清晰的 C/D/LLC/PFC 预设，不要按项目复制多份。

### 合并烧录工具 `IapFileCreator`

该工具根据 JSON 配置读取 bootloader 和 APP，写入 APP 大小、CRC，并生成 JLink 合并烧录文件。它的逻辑与 C/D 芯片版本无关。

建议统一由它生成：

- `*_JLink烧录.bin/.hex`
- `*_在线升级.bin/.hex`

后续建议：把 C/D、LLC/PFC 的地址、输入文件、输出文件都放到配置文件中，避免手工改路径。

## 条件共用工具

### 串口/CAN 转发板 `4. 转发板源程序/5.CommKit-5800`

这个目录不是普通 PC 工具，而是转发板固件。它的“协议功能”可以共用，但“底层驱动”取决于转发板自身使用的 MCU 和硬件。

可以共用的前提：

- 转发板硬件不变。
- 转发板自身 MCU 不换版本。
- 转发板 CAN/UART 引脚、时钟、波特率不变。
- 转发板只负责把外部 CAN 转成 LLC/PFC UART IAP 协议。

需要分版本的情况：

- 转发板 MCU 从 C 版本换到 D 版本。
- 转发板底层库、CAN/UART 初始化方式发生变化。
- 转发板协议需要新增安全握手或 CRC 校验。

结论：转发板协议层可以作为公共能力，但工程本身要按转发板硬件版本维护。

### `4.boot_config`

它的目标也是生成 bootloader + APP 的合并文件，理论上可以共用。但当前实现有较多硬编码路径和数据数组，不适合直接作为长期标准。

后续建议：

- 不再手动维护多份 C# 数组。
- 改成读取配置文件。
- 与 `IapFileCreator` 的职责合并或明确分工。
- 输出文件统一进入固定发布目录。

## 不能直接共用的部分

### Bootloader

bootloader 暂时必须按 C/D、LLC/PFC 分开验证。

原因：

- C 版本和 D 版本官方 SDK 不同。
- CAN、UART、Flash、时钟初始化可能不同。
- LLC 需要接外部 CAN，并可能负责转发 PFC。
- PFC 更适合做成只接受安全 IAP 命令的从设备。

当前目录策略是正确的：

- `3. bootloader/C版本bootloader`
- `3. bootloader/D版本bootloader`

后续等 C/D、LLC/PFC 都验证通过，再抽取公共 IAP 协议层，形成统一 bootloader 框架。

### APP 工程

APP 与具体项目和角色绑定，不能因为 IAP 协议类似就直接共用。

当前应继续分开：

- C 版本 227B-T LLC/PFC。
- D 版本 259B LLC/PFC。

APP 中只需要统一 IAP 相关约定，例如进入 IAP 命令、参数区地址、APP 起始地址、版本号规则。

## 推荐维护原则

1. PC 工具尽量共用，不按 C/D 复制。
2. 合并烧录工具统一配置化，不手工改路径。
3. 转发板按硬件版本维护，协议层尽量保持统一。
4. bootloader 先分版本验证，后续再统一架构。
5. APP 只统一 IAP 接口约定，不强行合并工程。

## 后续开发优先级

1. 保持 `CAN_TOOLS_NET8.0` 和 `11.iap_tools` 为两个通用上位机。
2. 将 `IapFileCreator` 作为统一烧录码生成入口。
3. 给 CAN 上位机增加 C/D/LLC/PFC 预设。
4. 给串口 IAP 工具增加同样的预设。
5. 完成 D 版本 PFC bootloader。
6. 回归 C 版本 LLC/PFC UART 和 IAP。
7. 验证四套路径后，再设计统一 bootloader 框架。
